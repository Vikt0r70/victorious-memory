  <action>
    **CRITICAL per D-03:** Do NOT modify the /health endpoint in main.py. The static {"status": "ok", "version": "0.1.0"} response is sufficient.

    **Step A — Dockerfile (apps/api/Dockerfile):**
    The python:3.12-slim base image does NOT include curl or wget. Add a RUN layer BEFORE the `COPY pyproject.toml .` line to install curl (lightweight, ~2MB):
    ```
    RUN apt-get update && apt-get install -y --no-install-recommends curl && rm -rf /var/lib/apt/lists/*
    ```
    This ensures the healthcheck command can probe the /health endpoint from inside the container.

    **Step B — docker-compose.yml:**
    Add a `healthcheck` block to the `api` service (at the same level as `depends_on:`, `restart:`, `ports:`). Follow the EXISTING db healthcheck pattern but adapt for HTTP:
    - `test: ["CMD-SHELL", "curl -f http://localhost:8080/health || exit 1"]`
      - `-f` flag makes curl return non-zero on HTTP errors (4xx/5xx)
      - `|| exit 1` is a safety net — ensures shell exits non-zero if curl itself fails (e.g., not installed, connection refused)
    - `interval: 10s` — slightly longer than db (5s) since api startup involves DB init + model loading
    - `timeout: 10s` — allow for slow first-start (HuggingFace model download on cold cache)
    - `retries: 10` — generous retries to cover cold-start model download (~60-120s worst case), combined with 10s interval = up to 100s startup grace period
    - `start_period: 40s` — Docker grace period before healthcheck failures count against retries; covers initial pip package scan + DB connection + worker start

    Place the healthcheck block after `depends_on:` and before `restart: unless-stopped`.

    Do NOT change: existing depends_on, dns, volumes, ports, env_file, environment, or restart policy. Do NOT change the db healthcheck.
  </action>
  <verify>

  </verify>

    - The healthcheck test command includes `curl -f http://localhost:8080/health || exit 1`

    2. **Inspect the matching container(s) for metadata:**
       For EACH container found matching the search:
       ```
       docker inspect CONTAINER_NAME_OR_ID
       ```
       Extract and record:
       - `Name` — container name
       - `Config.Image` — the Docker image
       - `Config.Labels` — any labels that identify purpose/owner
       - `Config.Env` — environment variables (mask any API keys: show `KEY=***` not the full value)
       - `NetworkSettings.Ports` — exposed/mapped ports
       - `Mounts` — volume mounts
       - `Created` — when the container was created

       If the container is running:
       ```
       docker top CONTAINER_NAME
       ```

       ```
       docker exec CONTAINER_NAME ps aux 2>/dev/null || echo "exec not available"
       ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Host → Docker daemon | Docker socket access controls container lifecycle; docker compose runs as current user |
| Docker network (api ↔ db) | Internal Compose network; db port 5432 exposed to host for dev access |
| Host → api:8080 | API port mapped to host; no auth — CORS allows all origins |
| Docker Hub → local images | Image pulls from Docker Hub (pgvector/pgvector:pg16, python:3.12-slim) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Spoofing | api:8080 (no auth) | accept | No auth is intentional for localhost deployment (PROJECT.md constraint). All origins allowed via CORS. Risk accepted for local development. |
| T-01-02 | Information Disclosure | docker-compose.yml published ports | accept | Ports 8080 and 5432 exposed to host. DB password via env var. Localhost-only deployment; network isolation is the security boundary. |
| T-01-03 | Information Disclosure | Brave MCnulty env vars | mitigate | Task 3 mandates masking API key values in BRAVE-MCNULTY.md (show `KEY=***` not plain text). |
| T-01-04 | Tampering | Dockerfile pip install (no hash pinning) | mitigate | Requirements in pyproject.toml are unversioned/pinned. Supply-chain risk accepted for dev phase. For production, pin hashes. |
| T-01-05 | Tampering | docker-compose.yml healthcheck command | mitigate | Healthcheck uses `curl -f` with `\|\| exit 1` — validates response integrity, fails on non-200. No secrets in health endpoint response. |
| T-01-06 | Elevation of Privilege | Docker Compose runs as host user | accept | Compose runs with user's permissions. No privileged mode, no docker socket mounting into containers. Standard practice for local dev. |
| T-01-SC | Tampering | pip install (Dockerfile) | mitigate | slopcheck protocol: if slopcheck tooling is configured, scan pip dependencies. Otherwise accept for Phase 1 — this is a health audit, not a dependency audit. |
</threat_model>
